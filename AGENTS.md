# Maintainer instructions

This repository is a development fork of `bremor/public_transport_victoria`.
Its immediate purpose is to add general, structured route alerts and contribute
that functionality upstream. It is not a commitment to a long-term maintained
replacement; see the README for the fork's intentions.

These instructions follow the workflow used in
[davidbmck/week-planner-card](https://github.com/davidbmck/week-planner-card/blob/main/AGENTS.md),
adapted for a Home Assistant Python integration.

Read the relevant GitHub issue completely before making changes. Issues are the
source of task-specific scope, dependencies and acceptance criteria; this file
contains standing rules. For a direct user request, use that request as the scope
and check relevant backlog issues. Explicit user instructions take precedence.
The route-alerts backlog is tracked in
[issue #1](https://github.com/davidbmck/public_transport_victoria/issues/1).

## Development principles

- Keep pull requests small, focused and single-purpose.
- Implement only the current issue or request. Do not opportunistically include
  later backlog items.
- Preserve the `public_transport_victoria` integration domain, existing config
  entries, departure entity IDs, unique IDs, names and attributes unless the task
  explicitly requires a change. Any required change needs a tested migration.
- Prefer fixing behaviour in the component responsible for it rather than adding
  dashboard templates, automations or other workarounds to hide integration bugs.
- Preserve existing behaviour outside the stated scope, including departure/run
  selection, timezone handling and polling intervals.
- Avoid unrelated formatting, dependency updates and refactoring.
- Do not commit generated bytecode, caches, virtual environments, downloaded data,
  database files, private configuration or credentials. Sanitise test fixtures.
- Do not change manifest versions, tags or release metadata unless the task is
  explicitly preparing a release.
- Preserve original project attribution and any licence information. Record
  provenance when adapting code from other forks.

If investigation reveals a separate bug or worthwhile improvement, create or
recommend a separate GitHub issue rather than folding it into the current PR.

## Maintenance direction

This fork prioritises:

- compatibility with current Home Assistant and existing installations;
- route alerts that work across transport modes, including general notices;
- current and planned notices with structured metadata and predictable date rules;
- alert polling that works even when no departures are available;
- explicit availability and recovery after API, network or Home Assistant failures;
- efficient shared requests with correct credential scope and lifecycle ownership;
- a focused implementation that remains suitable for contribution upstream.

For reliability work, use this design principle:

> Fetching new data may fail. A failed refresh must not be presented as a
> successful update or an empty alert feed.

Last-known-good data may be retained, but must not masquerade as fresh data from a
healthy feed. Keep alert and timetable failures independent. A successful empty
response means zero notices; an unsuccessful fetch means unavailable data.

Use Home Assistant's supported entity and coordinator interfaces and shared HTTP
session. Apply bounded request timeouts, consume responses within their context,
and avoid signed URLs or credential-bearing config entries in logs.

Do not hard-code V/Line-only alert categories or filter notices by English words
in their descriptions. Preserve IDs, status, dates and route/stop/direction
metadata. Follow the agreed issue contract for expiry and unknown dates.

Prefer incremental improvements to a wholesale rewrite.

## Workflow

Before editing:

1. Read the relevant issue or request, acceptance criteria and dependencies.
2. Inspect Git state and preserve unrelated working-tree changes.
3. Inspect the implementation, configuration conventions and surrounding lifecycle.
4. Check existing tests, workflows and documented public behaviour.
5. Work on a focused `codex/` branch based on the appropriate fork branch. Do not
   implement features directly on `master`.
6. Keep the planned change within the issue boundary.

Before opening a pull request:

1. Run the relevant behavioural and regression tests in an isolated development
   environment. Use mocked APIs and sanitised fixtures; do not require live
   credentials or a production Home Assistant instance.
2. Run the applicable documented formatting, syntax and integration-validation
   checks. For documentation-only changes, review the document and links; runtime
   tests are not required.
3. Run `git diff --check` and review the complete diff for unrelated changes,
   credentials and generated files.
4. Update documentation when public behaviour, attributes or configuration change.
5. Verify upgrade compatibility whenever setup, config flow or entity identity is
   affected. Cover two entries sharing a route, empty responses, missing fields,
   failures and unload/reload when relevant.
6. State exactly what was tested and what remains unverified. Do not claim that
   syntax checks or HACS metadata validation establish runtime correctness.

The upstream baseline currently has no behavioural test suite. Establish the
harness under backlog issue #6; inspect the available commands rather than
inventing test results or assuming test/release automation exists. The inherited
workflow is named "Validate with hassfest", but currently runs the HACS action,
not hassfest or behavioural tests.

Pull requests should:

- target this fork's `master`, unless an issue explicitly specifies another base;
- link the relevant issue, or explain the direct user request when no issue applies;
- explain the behavioural change, compatibility impact and validation performed;
- call out discovered follow-up work separately;
- never merge automatically.

Stop after opening the PR unless explicitly instructed to merge it. Do not open
upstream issues, comments or PRs unless the task authorises that contribution.

## Development and production boundaries

The development checkout is `/home/mckechnie/projects/public_transport_victoria`.
The live Home Assistant configuration is separate production infrastructure.

- Develop and test in this checkout or a disposable Home Assistant environment.
- Do not copy private configuration, `.storage`, registries, databases, tokens or
  household dashboard configuration into this public repository.
- Do not deploy into the live installation, reload integrations, restart Home
  Assistant, or operate physical devices as a side effect of development work.
  Production deployment requires an explicit task instruction.
- For an authorised deployment, inspect current state first, use supported Home
  Assistant interfaces, make the smallest change and verify application behaviour.
- Preserve the current integration source and local alert patch for rollback until
  any replacement has been verified. A successful install alone is insufficient.

## Releases and upstream contributions

Release work is tracked in issue #8 and upstream contribution work in issue #9.
Do not publish a release merely because the implementation has been committed.

- Verify installation and upgrade behaviour in a disposable Home Assistant
  environment, then perform any separately authorised production trial.
- Keep release tags and the integration manifest version consistent. Document the
  upstream base, actual validation, compatibility and rollback instructions.
- Verify the HACS installation layout; package the integration's Python source.
  There is no JavaScript build or `dist/` release asset for this project.
- Do not loosen repository-wide workflow permissions to make a release succeed.
  Required permissions belong on the specific workflow/job that needs them.
- Keep upstream PRs additive and focused, with tests and documentation. Separate
  broader maintenance or API migration work from the route-alerts feature.
- Do not promise continuing maintenance or a release schedule beyond the scope
  explicitly agreed with the user.
